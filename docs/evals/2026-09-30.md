# Evaluation: invented Perfect UI classes, with and without the skill and this server (T-pua-13)

- Date: 2026-09-30
- Question: do pages that coding agents build with Perfect UI 1.0.0 contain `pui-*` classes the library does not define, and does the `build-with-perfectui` skill plus this server remove them?
- Cases: the six requests in `evals/cases.json`, each followed by its instruction "Answer with one complete, self-contained HTML file and nothing else."
- Outputs: `evals/runs/2026-09-30/<model>/<case>/<variant>.html`; per-run cost, duration, tools called and where the HTML came from: `evals/runs/2026-09-30/runs.json`.
- Counted with: `npx tsx scripts/eval-markup.ts --runs evals/runs/2026-09-30/<model>` (corpus `data/corpus-1.0.0.json`, Perfect UI 1.0.0).

## Result

With the skill and the server, both models produced **0 invented classes in all six cases** (12 of 12 outputs), every output loaded the stylesheet pinned to `@chrissgon/perfectui@1.0.0`, and every run called `check_markup` before answering.

Without them, neither model knew the library: 10 of the 12 baseline pages use no `pui-*` class at all, so their count of 0 means "did not use Perfect UI", not "used it correctly" (see Caveats).

## Caveats

- **A baseline count of 0 is not a pass.** `check_markup` checks `pui-*` classes and 0.23 names. Ten of the twelve baseline pages contain no `pui-*` class: the models wrote their own CSS (Opus said so in one page) or linked packages that are not Perfect UI at `@latest` (`@perfect-ui/css`, `@perfectui/perfectui-css`). None of the twelve baseline pages loads Perfect UI 1.0.0.
- **0.23 names in baselines are coincidences.** `btn`, `card`, `badge`, `checkbox`, `switch` and `card-header` are the models' own unprefixed class names that happen to match classes of Perfect UI 0.23.0; none of those pages loads 0.23 either.
- **One run per case, variant and model.** No repetition, so the numbers show what happened once, not a rate.
- **The count covers class names only.** It does not check that the markup renders, that the structure matches the documentation, or that the page answers the request. One floor page (`dark-mode/skill-server`) imports `dist/js/mode.js` from the CDN, a file present in the 1.0.0 package; this was checked by listing the package, not by loading the page.
- **Where the HTML came from.** The driver takes the longest ```` ```html ```` block of the final answer, else a bare `<html>` document in it, else the largest `.html` file the model wrote in its folder (two floor baselines: `pricing`, `striped-table`; `runs.json` says which). Where a floor model both wrote a file and answered with the page, the answer was used; for `login-card/skill-server` the written file had two garbled CSS values that the answer did not, with the same classes.
- **Tool calls.** Opus loaded the skill in all six skill-server runs; one Opus baseline (`striped-table`) tried to run `ls` on its folder and a memory folder, which print mode denied. The floor model loaded the skill in all six skill-server runs too.
- **Cost of the strong model.** `total_cost_usd` is Claude Code's own price calculation for the tokens used; on a subscription login it is an estimate, not a charge.
